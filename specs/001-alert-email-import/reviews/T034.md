Failure mode on a malformed file during import: message is clear, but it surfaces as an exception out of `import_paths` (CLI `import-emails` prints a traceback ending in the ValueError message; `POST /api/import` would return a 500). The run is aborted at the first email, so emails of the same run already committed stay, the rest are not processed (they are not lost: re-run after fixing). This is defensible (every remaining email would fail the same way), but T035/CLI could catch ValueError and print a one-line message. Also `import_runs.error` stores only the type name `ValueError`, not the message; the file/entry text is lost from the run history.
2. Entries with extra keys next to valid ones (`note: hi`, or a typo like `categroy: house` beside valid `contains`/`category`) are accepted and the extra key ignored. The file format in config/alert_categories.yaml documents only `contains`/`category`, so rejecting unknown keys would be stricter and cheap; unclear, left as a choice.
3. Silent oddities still accepted: duplicate keys inside one entry (YAML last wins); a `contains` whose slug is empty (e.g. `'!!!'`) passes validation but `categorise` ignores the rule silently; `category` values are not stripped, so `' flat '` and `flat` count as two categories (reported as a conflict). Real edge cases, low likelihood.
