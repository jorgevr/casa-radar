## Findings

1. **Non-blocking (escalate to the user as a data-model question).** `app/main.py:90-92`: for a stored run,
   `problems` is rebuilt from `alert_emails`, so file-level failures (unsupported extension, unreadable or empty
   `.mbox`, which T018 counts in `n_failed` but never stores as rows) are missing from `GET /api/runs/{id}`. Probe:
   POST of `a.txt` returns `n_failed 1` with one problem; `GET /api/runs/{id}` of the same run returns `n_failed 1`,
   `problems []`. FR-002 / SC-004 / Article VI are met by the summary the import produces (the POST response, which
   the UI in T021 and the CLI show), so no email is silently skipped at import time. But the stored record of the run
   no longer says which file failed or why. Fixing this needs somewhere to persist file-level problems (`import_runs`
   or `alert_emails`). That is a data-model change outside the files T020 names, which is why I have not made it
   blocking. It should be decided before anything (US6, the Phase 9 sync UI that polls `GET /api/runs/{id}`) shows
   stored runs as their summary. The developer recorded the limitation in `handoffs/T020-dev.md`.

2. **Non-blocking.** `app/main.py:117-120`: a well-formed request can end in an unhandled `500 Internal Server Error`
   instead of a run summary or a 400. The cleaned-up name can be `.`, `..` or `...`, which resolve to the sub-folder
   itself. A long name also fails: on this machine (LongPathsEnabled = 0, `%TEMP%` path of about 57 characters) any
   name of about 196 characters or more raises `FileNotFoundError`, because the full temp path passes MAX_PATH. The
   whole batch is lost (no run is created, so nothing is stored half-way, and the temp folder is still removed), and
   the response does not say which file caused it. That goes against the contract's "400 only for a malformed request
   … response = run summary" and the "with evidence" part of Article VI. It is not silent, and real subject-based
   `.eml` names (about 80–90 characters, as in the fixtures) are well under the limit, so it is non-blocking.

3. **Non-blocking (contract gap).** `app/main.py:104`: `{"files": []}` is answered with 400. The contract does not
   say whether an empty list is "malformed". Nothing is dropped and no run is created, so Article VI is not affected.
   No test asserts this either way (`handoffs/T017-tests.md` lists it as a gap).

4. **Non-blocking.** `app/main.py:125`: `limit` outside 1..500 or not an integer returns FastAPI's 422, not 400. The
   contract does not cover `GET /api/runs` errors; the 500 cap is not in the docs.

5. **Non-blocking.** `app/main.py:117`: names are cut to their last segment and characters outside `[\w.\- ]` become
   `_`. That correctly stops path traversal: in the probe, `../x.eml`, `..\..\y.eml`, `C:\Windows\z.eml` and
   `/abs/w.eml` are all written inside the temp folder. The side effect is that `alert_emails.file_name` stores the
   cleaned name (e.g. `a_b.eml`, `x.eml`), whereas data-model says "name as supplied". `problems[].email_id` for
   file-level failures is also the cleaned name or `file`.

6. **Non-blocking.** `app/main.py:98, 121`: the import is an `async def` endpoint that runs blocking SQLite and parsing
   work on the event loop, so the server answers nothing else (static files, other API calls) until the import
   finishes. This follows the existing `import-csv` endpoints (`app/main.py:54, 153`). The single connection is opened
   with `check_same_thread=False` (`app/db.py:84`), and `sqlite3.threadsafety` is 3 here (SQLite serialized mode), so
   the shared connection cannot crash. Transactions can still interleave, though: a sync handler already running in
   the threadpool when the import starts (for example a slow `POST /api/listings/{id}/amenities` that ends with a
   `commit`) can commit part of one message's `with conn:` transaction early. If that message then fails, it could be
   left half-written. This hazard comes from the existing shared-connection design and needs overlapping requests in a
   single-user tool, so it is non-blocking now. It becomes real when the Phase 9 scheduled sync writes from a
   background thread.

7. **Non-blocking.** `app/main.py:114-121`: raw emails, which include personal data, are written briefly to the
   system `%TEMP%`. That is outside the repository and on the local machine, so Article III is met. The folder is
   removed on success and on exceptions (probe: no `casa-import-*` folders left after the 500 cases). It would only
   be left behind if the process were killed mid-import. Holding the decoded base64 bodies in memory is not a real
   risk for a single-user tool on localhost.

8. **Non-blocking (test coverage).** `tests/test_api_alerts.py` has no test for: the path-traversal cleanup of `name`
   (finding 5); a file-level failure (for example a `.txt` name) giving 200 with a `failed` problem through the API;
   or the content of `GET /api/runs` list items beyond the counts. The behaviour the tests do cover is
   correct and hand-derived.

No blocking findings.
