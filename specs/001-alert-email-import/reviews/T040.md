## Findings

1. FAIL-level (atomicity), app/main.py:171-177 and :181-184. An integer outside SQLite's 64-bit range
   (e.g. `{"notes":"X","price":10**30}`, or `bedrooms` 10**30) passes validation (`isfinite(10**30)` is true) and
   raises OverflowError from the UPDATE (HTTP 500). By then `status`/`notes` UPDATEs have run on the shared
   connection and are not rolled back; the next request's commit persists them. Reproduced: PATCH returned
   OverflowError after notes was written to the pending transaction. This breaks the all-or-nothing behaviour.
   Fix: reject ints beyond the SQLite range (or coerce price/area to float and bound bedrooms), and/or wrap the
   writes in try/except with `conn.rollback()`. Add a test for it. Also note 1e308 is accepted (list still 200),
   a sane upper bound would be cleaner but is optional.

2. Low, not blocking. app/main.py PATCH does not write price_history for a manual price. FR-007 and data-model
   (non-alert rows left alone) do not require it, so no violation. Consequence for FR-034: after the user chooses
   a unit, `momentum` (scoring.py `history[0]/history[-1]`) is computed from the history of the development's
   stated price, so an earlier drop of the development price is read as a drop of the chosen unit. Consider
   recording a manual history row or resetting momentum for user-chosen units; needs a spec decision.

3. Low. `tipo desconocido` (flag table) is not implemented; property_type is never null and T037 does not test it.
   Acceptable, noted in the T040 handoff.

4. Info. Unchosen development with a stated price above max_price shows `precio > ...` in flags (not exclusion);
   consistent with R13 "flag instead of excluding".
