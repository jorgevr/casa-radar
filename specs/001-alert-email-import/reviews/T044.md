## Findings

### F1 (medium, should fix): reprocess runs show no problems in `GET /api/runs[/{id}]`
`app/main.py:239` selects problems with `first_run_id=? AND outcome IN ('rejected','failed')`. Reprocess keeps `first_run_id`
and sets only `last_run_id`, so the run detail of a reprocess run lists none. Probe: POST reprocess with one still-failing
email returns `problems` length 1 and `n_failed` 1, but `/api/runs/{run_id}` returns `problems` length 0 with `n_failed` 1.
The contract (api.md "Runs and emails") gives every run a `problems` list; the Datos tab history will contradict its own
counters. Fix: for kind `reprocess` match `last_run_id=?`. Needs a test.

### F2 (medium, should fix): a malformed categories file overwrites every re-read email's category with "unknown"
`app/alerts.py:281-283` falls back to `rules=[]` (copied from the import path); the UPDATE (line ~300s) then writes `category`
and `category_rules_matched`, and `_record_sighting` stores the category on the new sighting. With `scope="all"` and a bad
rules file, probe: category `house` became `unknown` on both `alert_emails` and `sightings`, category-derived new-build
suggestions are dropped on re-derive, and the run ends `ok` with only `error="ValueError: bad"`. At import the fallback is
acceptable (new data); on reprocess it destroys previously good derived values. Recoverable (raw intact, rerun after fixing
the file) but silent apart from the run note. Fix: on rules load failure abort the run (status `failed`, no changes) or keep
each email's stored category.

### F3 (low/medium, justify or fix): sightings are deleted when an email stops being readable or moves listing; the listing is left behind
- Email stops reading (probe C, scope all): its sightings are deleted, `derive_listing` returns early on zero sightings
  (`app/derive.py:59`), so the listing keeps price, first/last seen and alert price_history but has no sighting and no email
  as source (FR-004 provenance lost). The dev justification (FR-011: never blank known values; FR-009: failed emails must not
  change a listing) covers the values, but deleting the sighting is itself a change driven by a failed email, and the data
  diverges from a fresh import (which would have no listing). Raw is retained (Article IX), so it is recoverable. Acceptable
  if documented in data-model/spec; better, keep the old sightings when the new read does not produce `imported`.
- Sighting moves to another code (probe A): old `idealista:112842548` stays with price 645000, price_history and `last_seen`
  and zero sightings; a new listing is created. Never deleting listings is a safe default, but R11's "same as fresh import"
  does not hold here. Needs a reader change that alters the listing code, so low.
- Same cause: a newer reader that yields null for a field leaves the old value (FR-011 fallback in `derive_listing`). Intended.

### F4 (low): reader_version compared as strings (`app/alerts.py:286`, `reader_version < ?`)
`idealista-YYYY.MM` compares correctly only while the month is zero padded. Checked: `"idealista-2026.9" < "idealista-2026.10"`
is False, so an unpadded version would make failed emails look newer and be skipped silently; a prefix rename also breaks
ordering. Recommend `reader_version IS NULL OR reader_version != ?` (a downgrade then also reprocesses, harmless), or pin the
zero-padded format in a test/comment. Not blocking.

### F5 (low): one exception aborts the whole run
`app/alerts.py:317` re-raises after marking the run failed. One email that makes the reader raise (or a NULL `raw`; the column
is nullable, app/db.py:47) stops all later emails and, being first by date, would block scope `failed` every time. Per-email
atomicity is right; consider recording that email as failed (exception class only) and continuing. Not blocking: the reader
returns Problems rather than raising on known shapes.

### F6 (low, informational)
- `POST /api/alerts/reprocess` (`app/main.py:293`) is `async def` running blocking SQLite on the event loop while sync handlers
  (thread pool) share the single `check_same_thread=False` connection; a concurrent write handler's commit could commit a
  half-done email. Same pattern as `/api/alerts/import`; single-user tool, acceptable.
- Listings only touched by a moved-away sighting are not counted in `n_updated_listings`; counters understate changes.
- `GET /api/alerts/emails` has no limit; six small columns per row, fine at single-user scale.

## Verdict
No violation of raw data, hash or first_run_id; per-email atomicity and idempotency hold; derivation equals a fresh import in
normal cases; the HTTP surface is safe. F1 and F2 are real defects worth fixing before the Datos tab (T046) relies on them,
but neither corrupts raw data and both are recoverable, so they are follow-ups, not blockers.
