## Findings

### Blocking

1. **`app/alerts.py:170-175` / `app/alerts.py:198-207`: a supplied `.mbox` that yields zero messages is
   dropped silently (Article VI Fail Loudly; SC-004, FR-002).** I tested an `.eml` saved with an `.mbox`
   name (no leading `From ` line). The result was `n_found=0`, `status=ok`, `problems=[]`, and the email it
   contains is not reported anywhere. The same happens with an empty or truncated mbox. `mailbox.mbox` also
   skips any content before the first `From ` line without a word. The user supplied a file and the summary
   says nothing about it, which is what Article VI ("unexpected shapes fail with evidence") and SC-004
   ("100% of emails … supplied as files appear in that summary") forbid. The developer handoff names this
   case and leaves it out. No test covers it.

### Non-blocking observations

2. **`app/alerts.py:158-159`: non-`.eml`/`.mbox` files inside a folder are skipped silently**, including
   `.msg`. Probe: a folder holding only `a.msg` and `b.txt` gives `n_found=0`, `status=ok`, no problems.
   This matches the task text ("expand folders … to `*.eml`/`*.mbox`") and contracts/cli.md ("a folder
   means every such file inside it"), so it is not a defect against the task. It does mean the
   "save as .eml" message only reaches a user who names the `.msg` file directly. A folder of Outlook
   exports reads as "0 emails" with no explanation (spirit of Article VI and US4). The user should decide
   whether that is acceptable.
3. **`app/alerts.py:161,176,206`: a missing path without a suffix (e.g. a mistyped folder name) is reported
   as `unsupported file format: save as .eml`.** It is counted (1 found, 1 failed), but the evidence is
   wrong: the problem is that the path does not exist, not its format (Article VI "with evidence"). A
   missing `.mbox`/`.eml` correctly gets `unreadable file…`.
4. **`tests/test_alerts_import.py`: three T018 behaviours have no test.** These are oldest-`Date`-first
   ordering, non-recursive folder expansion, and the exact `#index` mapping (only the prefix and
   distinctness are asserted). The `.msg` test (`tests/test_alerts_import.py:84-93`) does not check
   `sum = n_found` or the outcome. T016's text does not ask for these, so this is coverage, not a broken
   criterion. My probe confirmed the code: in an mbox ordered [2026-10-23 with no Date, 2026-10-28, 2021],
   processing ran 2021, then 2026-10-28, and the Date-less message last, which failed with
   `REASON_NO_DATE`. The fixture folder's name order differs from its Date order (several fixtures on
   2026-10-23 and 2026-10-27), so ordering does run, but nothing asserts it.
5. **`app/alerts.py:220-222`: only `Exception` is caught.** A `KeyboardInterrupt` (Ctrl+C during a long CLI
   import) leaves the run in `status='running'` with `finished_at` null. data-model has an `interrupted`
   status for this. The exception path itself is fine. Probe with the reader raising
   `RuntimeError("secret content here")`: run `failed`, `error='RuntimeError'` (class name only, no content
   leaked), `finished_at` set, exception re-raised. Earlier messages stay committed in their own
   transactions; the failing one is rolled back.
6. **`app/alerts.py:198-208`: every message of every file is read into memory before processing.** That is
   needed to sort by Date and is fine for the target sizes (SC-001: 30 emails). Noted only for very large
   mbox exports. No action required by the task.
