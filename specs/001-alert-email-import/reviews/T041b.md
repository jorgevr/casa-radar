## Findings
1. Scope of the change. `rank()` now loads `listings` first, builds `user_priced` from `field_sources.price in USER_ORIGINS`
   (manual, csv), and skips only `price_history` rows with origin `alert`/`alert_previous` for those ids. For every other
   listing the loop body is the same as before (same query order `HISTORY_ORDER`, same append), so behaviour is unchanged
   for: price source `alert`, `api`/`idealista_api` or any non-user value, absent key, null/empty `field_sources`.
   The guard tests cover `alert` and absent.
2. Malformed/missing `field_sources`: `_price_is_user_owned` catches TypeError/ValueError, returns False for non-dict JSON
   (list, string, number, null) and for missing/empty values. A malformed value therefore falls back to the old behaviour
   (series kept), which is the safe direction (no imputation, no crash). Not covered by a test (minor, see recommendations).
3. Other origins in a user-priced listing: manual/csv-origin history rows and legacy null-origin rows stay in the series.
   Judgement: skipping only alert rows is right. Momentum is a function of the price series; what T041b removes is the
   series that no longer describes the price (FR-007: alert changes are not recorded over a user-entered price; derive builds
   no alert rows for it). Docs never say user-entered or legacy rows must be dropped, and dropping them would silently
   discard user data (Article I spirit). Caveat for the record: for a user-priced listing with legacy rows only, momentum is
   computed from legacy first/last, not from the current user price; this is pre-existing behaviour and out of scope.
   Recommendation: keep as is.
4. Real flow was already correct (derive sets history empty and `_write_price_history` deletes alert rows); the change is
   defensive for stored rows left by older state or paths that do not re-derive. It is small and consistent with the task
   ("scoring.py and/or main.py, whichever is smaller").
5. Price-history route / "antes del <fecha>": the route is unfiltered, the UI shows "antes del" only for `alert_previous`.
   In the real flow a user price leaves no alert rows (tested), so the route and the ranking agree; no contradiction.
   Directly seeded stale alert rows would still show in the route but not in momentum; the task and spec do not require
   the route to filter, and the dev handoff records this decision. Acceptable.
6. SCORING_VERSION stays 2 (pinned by a test). No new literals: `("alert", "alert_previous")` mirrors the origin names
   already used in derive/data-model; the 0.10 saturation is the existing pre-change constant. A shared constant for the two
   origin names would be tidier but is not required.
7. Hand calculation verified independently: series 800.000 -> 600.000 gives drop = 1 - 600000/800000 = 1 - 0.75 = 0.25 = 25 %;
   formula is clamp(drop/0.10) = clamp(2.5) = 1.0 (clamped to 1), flag "bajada de precio acumulada 25.0%". The test
   docstring derives it by hand and the guard tests pin the same numbers on a non-user-priced listing, so expected values
   do not come from the code under test. Tests were written first and the two rank() tests failed for the right reason
   (momentum 1.0 instead of None) per the tests handoff.
